# 转化归因链路 & 发布保护机制 · 使用说明

> 适用版本：麦屿手作官网 v1.x（展示型官网，**不含在线支付**）
> 本文回答两个问题：① 官网到底带来了多少单，凭什么这么算？② 改内容怎么才能不把线上改坏？

---

## 第一部分 · 转化归因链路

### 1. 为什么需要这一层

展示型官网的转化**不发生在网站上**，而发生在电话那头：

```
访客看官网  →  打订购电话  →  客服接单  →  线下收款
   ↑ 有数据（埋点）        ↑ 有数据（通话记录）        ↑ 有数据（订单台账）
              ↑↑↑ 这两段原来完全断开，官网无法证明自己的价值
```

所以归因的全部工作，就是**把「谁在什么时候访问过官网」和「谁在什么时候打了电话」接上**。接上之后，「官网带来多少单」才是一个能拿去要预算的数字，而不是一句感觉。

### 2. 数据字段匹配方式（三段接线）

#### 接线一：访客 ↔ 访问行为（前端埋点 → 后端会话）

| 字段 | 生成方 | 存放位置 | 说明 |
|------|--------|----------|------|
| `visitor_id` | 前端 `tracker.ts` | 浏览器 `localStorage`，365 天 | 同一台设备同一个人，换会话不变 |
| `session_id` | 前端 `tracker.ts` | 浏览器 `sessionStorage`，空闲 30 分钟重建 | 一次「连续浏览」= 一个会话 |
| `channel` / `channel_detail` | 后端 `detect_channel()` | `visitor_session` 表 | 靠 `utm_*` + `referrer` 推断 |
| `first_seen_at` / `last_seen_at` | 后端写库时 | `visitor_session` 表 | 时间窗匹配的两根指针 |
| `page_view_count` / `hotline_click_count` | 后端累加 | `visitor_session` 表 | 漏斗中间层 |

明细事件落在 `visit_event`：`page_view` / `cake_view` / `hotline_click` / `message_submit`，带 `page_path` 与 `ref_object_type`+`ref_object_id`（看的是哪个蛋糕）。

#### 接线二：访问行为 ↔ 来电（**归因的核心一跳**）

靠**两个独立证据**交叉验证，缺一不可：

**证据 A —— 号码来源证明（追踪号码）**
不同渠道的访客在页面上看到**不同的订购电话**，电话响了就知道这通电话从哪来。

| 字段 | 表 | 作用 |
|------|-----|------|
| `tracking_number.tracking_no` | `tracking_number` | 真实被拨打的号（唯一键） |
| `tracking_number.display_no` | `tracking_number` | 页面上展示的号（可与真实号不同，接呼叫转移） |
| `tracking_number.channel` / `channel_detail` | `tracking_number` | 这个号属于哪个渠道 |
| `call_log.tracking_no` | `call_log` | 接线员录入时选/填的「客人打的是哪个号」 |

**证据 B —— 时间接近证明（时间窗）**
`call_log.called_at`（来电时间）与 `visitor_session.last_seen_at`（最后活动时间）比对，默认窗口 **30 分钟**（可配）。

匹配逻辑（`server/app/utils/attribution.py::attribute_call`）：

```
候选会话 = 全部会话中满足：
    last_seen_at  >= called_at - 30 分钟      ← 最近还在站内
    且 first_seen_at <= called_at             ← 不是打完电话才进站的
    且 is_bot = false                         ← 排除爬虫
优先取 channel 与 tracking_number.channel 相同的会话；
同渠道没有候选时，才放宽到全部渠道（但置信度会降级）。
```

> ⚠️ 这里踩过一个坑，值得记下来：最初的判据是「`last_seen_at` 必须早于来电」。
> 这在纸面上很直觉，实际会漏——客服常在下班前批量补录，顾客可能挂断后还在浏览，
> `last_seen_at` 就落到 `called_at` 之后了，本该是强归因的电话被降成渠道级。
> 改用「**会话开始**不得晚于来电」后，既不会漏掉仍在线的人，也不会把来电之后才进站的新访客算进来。

#### 接线三：来电 ↔ 订单金额

| 字段 | 表 | 作用 |
|------|-----|------|
| `order_attribution.order_id` / `order_no` | `order_attribution` | 挂到订单台账上 |
| `order_attribution.call_id` | `order_attribution` | 指向归因成功的那通电话 |
| `order_attribution.amount` | `order_attribution` | 金额（**只有可归因的才计入「官网带来」**） |
| `call_log.caller_phone_hash` / `order.customer_phone`(哈希后) | 双方 | 同号 → 继承该来电的归因结果 |

⚠️ 手机号一律 **SHA256 + 固定盐** 落库（`caller_phone_hash`），明文只留掩码 `138****5678`。归因系统同时接触行为和号码，落明文它就变成比官网本身更危险的信息库。

### 3. 归因规则（四级，按优先级命中即停）

| 规则 | 判据 | 置信度 | 归到哪一级 | 能不能进「官网带来 GMV」 |
|------|------|--------|-----------|------------------------|
| **R1** `R1_TRACKING_WINDOW` | 打了官网专属号 **且** 时间窗内有人访问 | `high`（多候选降 `medium`） | 访客级（能说出是谁） | ✅ 可 |
| **R2** `R2_TRACKING_ONLY` | 打了官网专属号，但窗内没人 | `medium` | 渠道级（只知道从哪来） | ✅ 可，但要标注「不含访客」 |
| **R3** `R3_PHONE_LASTTOUCH` | 打的是普通号，但手机号历史上访问过官网 | `medium`（订单反查则 `low`） | 访客级（跨设备） | ⚠️ 算「官网有影响」，单独一列 |
| **R4** `R4_UNMATCHED` | 全不命中 | `none` | **不归因** | ❌ 不算 |

**三条硬性闸门（防虚高，比防漏更重要）：**

1. **非官网号码一律不算**：打的号不在 `tracking_number` 表里 → `is_attributable=false`，直接 R4。自然到店客流被算成官网业绩，报表会系统性虚高，老板拿这个数字投广告就会亏钱。
2. **测试/错号不进分母**：`status` 为 `test` / `wrong_number` 的来电，在报表分母里就被剔除。
3. **爬虫不进分母**：`is_bot=true` 的会话不计入漏斗分母；无 UA 的请求一律按机器处理（宁可少算）。

**归因结果一经写入不自动变更**。要重算必须显式调用 `POST /admin/attribution/calls/{id}/reattribute`，并留痕——否则「昨天给老板的报表数字今天变了」这种事故永远查不出原因。

### 4. 覆盖的渠道与场景

**渠道识别**（`detect_channel`，优先级从高到低）：

| 优先级 | 判据 | 一级渠道 | 细分示例 |
|--------|------|---------|---------|
| 1 | `utm_source`/`utm_medium` ∈ qr | `qr_offline` | 门店海报二维码、包装盒二维码 |
| 2 | `utm_source`/`utm_medium` ∈ sms | `sms` | 会员短信、活动通知 |
| 3 | `utm_medium` ∈ cpc/sem/feed/display | `paid` | 小红书信息流、百度竞价、大众点评 |
| 4 | `referrer` 域名命中社媒 | `social` | 小红书、微信、微博、抖音、知乎、B站 |
| 5 | `referrer` 域名命中搜索 | `organic_search` | 百度、搜狗、360、神马、头条搜索 |
| 6 | 无 referrer 且无 utm | `direct` | 收藏夹、直接输网址、App 内打开 |
| 7 | 站内跳转 | `direct`（`internal`） | 不把站内跳转误算成外链 |
| 8 | 其他外链 | `referral` | 本地美食号、友情链接 |

**必须覆盖的 8 个业务场景：**

| # | 场景 | 走哪条规则 | 要注意什么 |
|---|------|-----------|-----------|
| 1 | 小红书笔记看到 → 点进官网 → 打电话 | R1 | 页面必须给小红书访客展示小红书专线 |
| 2 | 门店海报扫码 → 看菜单 → 打电话 | R1 | 二维码必须带 `utm_source=qr`，否则判成 direct |
| 3 | 百度搜到 → 直接拨页脚号码 | R1/R2 | 搜素落地页也要下发专属号 |
| 4 | 老客户直接拨门店普通号 | R4 | **不能算官网业绩**，但若手机号绑过则升 R3 |
| 5 | 手机看官网 → 用座机打电话 | R3 | 靠留言/订单绑定的手机号回溯（默认回看 7 天） |
| 6 | 朋友转发链接，对方看完打电话 | R1（渠道 referral/unknown） | 转发带来的是 referral，不要并进 social |
| 7 | 顾客先打电话，再看官网比价 | R4 | `first_seen_at` 晚于 `called_at`，**不能**算官网带来 |
| 8 | 投放落地页 A/B 两条专线 | R1/R2 + `channel_detail` | 一线一号，否则分不出哪个素材有效 |

### 5. 报表怎么看（口径必须一起看）

`GET /admin/attribution/report?days=30` 固定返回四块，**业绩与质量并排**，不允许只给一个漂亮总数：

| 块 | 内容 | 使用注意 |
|----|------|---------|
| `funnel` | 有效会话 → 热线点击 → 来电（可归因）→ 成单 → 金额 | 分母已剔爬虫；`call_rate` 为 null 表示分母为 0，不是 0% |
| `attribution_quality` | R1~R4 各自数量与占比 + **访客级归因率** | 访客级归因率 = (R1+R3)/总来电，这是「链路真的接上了」的比例 |
| `channels` | 逐渠道 会话/点击/来电/成单/金额/转化率 | 按金额降序，一眼看出哪个渠道真出钱 |
| `rules` | 当前生效的时间窗、回溯天数等 | 口径随报表返回，谁看都是同一份数 |

**对外报数的一句话规定**：说「官网带来 X 单」时，默认只算 R1+R2；R3 单独说「官网有影响 Y 单」；R4 不提。四级合计**不是**官网业绩。

### 6. 日常操作

| 谁 | 做什么 | 怎么做 |
|----|--------|--------|
| 运营/老板 | 给每个渠道配专属号 | `POST /admin/attribution/tracking-numbers`（一线一号，`channel` 必填） |
| 客服 | 每通电话录一条 | `POST /admin/attribution/calls`，填 `caller_phone` + `called_at` + `tracking_no`；**保存即自动归因**，返回里直接带回 R1~R4 结果 |
| 老板 | 月底看数 | `GET /admin/attribution/report?days=30` |
| 技术 | 调整时间窗 | `PUT /admin/attribution/rules/session_window_minutes`（默认 30 分钟，改完对新来电生效） |

> 已产生的历史来电，号码**不能物理删除**（会被自动改为停用 `is_active=false`），否则历史报表会失去渠道归属。

## 第二部分 · 发布保护机制

### 1. 解决什么问题

原来的保存是「点了就上线」。一次误删、一次把草稿文案存上去，顾客当场就能看到。发布保护要保证三件事：

1. **看不见的改动不会上线**（草稿隔离）
2. **上线前有人真的看过**（预览）
3. **上错了能退回去，且退的过程有记录**（回滚 + 留痕）

### 2. 数据结构与状态机

三张表，全部**只追加，不覆盖、不删除**：

| 表 | 承载什么 | 关键字段 |
|----|---------|---------|
| `content_version` | 每一次内容快照 | `key`、`version`（同 key 内自增）、`value`、`content_hash`、`status`、`is_current`、`based_on_version`、`rollback_from_version`、`change_summary`、`created_by` |
| `content_publish_log` | 每一次动作的审计 | `action`（draft/preview/publish/rollback/offline/fail）、`operator`、`result`、`detail`、`created_at` |
| `content_preview_token` | 预览临时凭证 | `token`、`key`（强绑定）、`version_id`、`expires_at`、`max_uses`、`revoked_at` |

版本状态：`draft`（草稿）→ `published`（线上）→ `superseded`（被新版顶替）/ `rolled_back`（被回滚顶替）。
同一 key **任何时刻有且只有一个** `is_current=true`。

### 3. 预览：预览的是「内容」，不是「页面外观」

| 项 | 规则 |
|----|------|
| 预览对象 | **某一版草稿的内容值**（`content_version.value`），按该 key 的正常渲染方式显示 |
| 预览入口 | `POST /admin/content/{key}/preview-token` → 返回 `preview_url` |
| 链接形式 | `/?preview_token=xxx&preview_key=brand_story`（参数必须在 `#` 之前，才能被服务端读到） |
| 有效期 | 默认 30 分钟，限次数，**只能看绑定的那个 key**（拿 A 的令牌看不到 B） |
| 失效时机 | 到期 / 次数用尽 / 该 key 发布新版本时立即吊销 |
| 读不到时 | **不报错**，降级返回线上内容并带 `preview_invalid=true`，页面顶部横幅明确提示「预览已失效，当前显示的是线上内容」 |
| 预览期线上 | 完全不受影响，顾客看到的还是旧版 |
| 令牌保险 | 前端读到后立刻从地址栏抹掉，避免链接被截图转发成长期后门 |

### 4. 发布流程

```
① 保存草稿          POST /content/{key}/draft   {value, based_on_version}
        ↓（线上不动，可反复改）
② 生成预览链接      POST /content/{key}/preview-token
        ↓（自检 + 给老板/运营过目）
③ 发布              POST /content/{key}/publish  {version_id, change_summary}
        ↓（change_summary 必填，非空才允许发布）
④ 线上生效 + 旧版本置 superseded + 旧预览令牌全部吊销 + 写审计日志
```

**并发保护（不允许静默覆盖别人的修改）**：
保存草稿带 `based_on_version`。若此时线上/版本链已经前进（别人先发了新版），服务端返回 **409** 并说明当前版本号，前端必须提示「内容已被他人更新，请刷新后再改」。**不允许**用「后写覆盖先写」蒙过去。

**快速通道（保留兼容）**：`PUT /content/{key}` 仍是「保存即生效」，但**也会写一条版本记录**（`change_summary` 标记为快速通道）。这样即使运营走了老路径，历史照样可追溯、照样能回滚——不会出现「内容变了但版本链里没有」的断点。

### 5. 回滚：造新版本，不是把指针拨回去

| 项 | 规则 |
|----|------|
| 做法 | 复制目标版本的内容 → 生成**一个新的版本号** → 设为当前 |
| 版本号 | 只增不减。回滚到 v1 之后，当前版本是 v4（不是 v1） |
| 记录 | 新版本 `rollback_from_version=1`、`status=rolled_back` 的旧版保留、`change_summary` 记录「回滚：原因」 |
| 原因 | **必填**，非空才允许执行 |
| 可逆 | 回滚本身也能被回滚（再滚回 v2 即可），因为 v2 的内容一直在版本链里 |
| 拒绝 | 回滚到「已是当前版本」直接 400，不做无意义动作 |

**触发条件（满足任一条就该回滚）：**

1. 线上出现**事实错误**：价格、电话、地址、营业时间写错
2. 线上出现**展示异常**：区块空白、图片裂开、文案溢出/错位
3. 上线后**顾客反馈看不懂/被误导**（例如把「定制说明」写成硬性承诺）
4. 上线内容**不合规**（广告法禁用词、未经授权的图片）
5. 新版**数据异常**（例如把 4 张 Banner 存成 0 张，首页主视觉消失）
6. 发布**发错了 key**（本该改「联系我们」，改成了「订购信息」）

### 6. 紧急下线

`POST /admin/content/{key}/offline`（原因必填）：把该 key 的线上内容置空，前台对应区块自动隐藏。
**版本历史一条不删**，随时可用回滚恢复。适用场景：内容被举报、图片侵权、文案需要立刻撤下但来不及改。

### 7. 版本留痕要求（可验收的硬指标）

| 要求 | 判据 |
|------|------|
| 每次内容变化都有版本记录 | `content_version` 行数 = 保存/发布/回滚/下线动作次数 |
| 版本号连续不重复 | 同 key 内 `version` 严格递增、无重号 |
| 历史不可删改 | 不存在 DELETE 接口；旧版本只变 `status`，`value` 不动 |
| 任何时刻只有一个当前版 | `is_current=true` 的行数 ≤ 1 |
| 每步都有操作人与时间 | `content_publish_log` 每行都有 `operator`、`created_at` |
| 失败也留痕 | 发布失败/409 冲突同样写一条 `action=fail` 的日志 |
| 全部五类动作可查 | `GET /admin/content/publish-logs` 能查到 draft/preview/publish/rollback/offline |

### 8. 关键异常场景处理

| # | 异常场景 | 系统的行为 | 人工该做什么 |
|---|---------|-----------|-------------|
| 1 | 两人同时改同一个内容 | 后保存者收到 **409 版本冲突**，线上不被覆盖 | 刷新、看差异、重新改 |
| 2 | 预览链接发到群里被转发 | 令牌绑定 key + 限时限次 + 发布即吊销 | 无需处理；必要时重新生成 |
| 3 | 预览链接过期后被人打开 | 200 + 线上内容 + 顶部「预览已失效」横幅，**不报错** | 重新生成令牌 |
| 4 | 发布时忘了写变更说明 | 后端 400 拒绝 | 补一句「改了什么」 |
| 5 | 发布后发现内容错了 | 回滚到上一版本（造新版本） | 填回滚原因，事后在日志里能查到是谁、为什么 |
| 6 | 回滚后又发现旧版也有问题 | 再回滚到更早的版本 | 版本链只增不减，任意历史版都能回到 |
| 7 | 内容必须立刻撤下 | `offline` 置空 + 前台区块隐藏 | 事后用回滚恢复或重新编辑 |
| 8 | 内容校验不通过（字段缺失/类型错） | 草稿、发布、快速通道**共用同一套校验**（`content_rules`），三处行为一致 | 按提示补字段 |
| 9 | 数据库里内容被手工改乱 | 与 `content_version` 对不上时，以版本链最后一条 published 为可信来源回滚 | 不要手工改库；改内容走接口 |
| 10 | 首次部署，版本表是空的 | 第一次访问版本接口时**自动建立 v1 基线**（用当前线上内容），不会凭空造版本 | 无需处理 |

## 附录 · 接口与文件清单
