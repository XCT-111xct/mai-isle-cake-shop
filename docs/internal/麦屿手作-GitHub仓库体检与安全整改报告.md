## 三、JWT 密钥这件事：已修好，并且不需要清洗 git 历史

### 3.1 原来的问题链

```
config.py 写死密钥
      ↓（配置层不读环境变量，无处覆盖）
密钥随代码提交进公开仓库
      ↓（用同一个字符串当签名密钥）
任何人本地跑一段 python 就能签出合法管理员 Token
      ↓
直接调 /api/v1/admin/* 全部接口，不需要密码、不需要登录页
```

这不是"理论上可能"，是 `python-jose` 的标准用法，十几行就能复现。

### 3.2 本次改了什么（4 处，全部已实测验证）

| 改动 | 文件 | 说明 |
|------|------|------|
| 配置全面环境变量化 | `config.py` | 新增 `MAI_ISLE_SECRET` / `MAI_ISLE_ENV` / `MAI_ISLE_DEBUG` / `MAI_ISLE_CORS` / `MAI_ISLE_UPLOAD_DIR` / `MAI_ISLE_DB_PATH` / `MAI_ISLE_PORT`；读取顺序「环境变量 > 开发默认值」 |
| 启动前安全体检（fail fast） | `config.py` | 生产环境下，密钥仍是默认值、或长度 < 32 字符、或 DEBUG 被打开 → **直接抛异常拒绝启动** |
| 生产关闭接口文档页 | `main.py` | `docs_url/redoc_url/openapi_url` 按 `IS_PROD` 置 None，避免公开完整接口地图 |
| 补上 CORS 中间件注册 | `main.py` | 原代码 `import CORSMiddleware` 但**从未 `add_middleware`**（配置项写了却不生效）；现已注册，白名单来自 `settings.CORS_ORIGINS` |
| 新增配置样例 | `server/.env.example` | 逐项注释说明，可安全公开；真实 `.env` 仍被忽略 |

### 3.4 历史里的旧密钥要不要清洗 git 历史？

**结论：不需要。** 这里容易被"泄露了就完了"的直觉带偏，讲清道理：

- 需要洗历史的凭据是那些**一泄露就永久有效**的：云厂商 AK/SK、数据库密码、支付密钥。它们泄露后唯一的解是立即作废重发。
- JWT 密钥不是这类。它只是"签名用的印章"，风险取决于**有没有用它盖过真章**。本项目从未公网运行，**没有任何真实 Token 是用这个密钥签发的**，所以它现在只是四个普通英文单词拼起来的占位串——文件里明写着 `change-in-production`。
- 重写历史的代价：force push、所有 commit hash 变化、已有 fork 失效、操作失误可能丢提交。收益约等于 0。

**但有一个必须确认的前提**——请老大自己回答：

> ❓ **这份代码有没有曾经部署到公网（哪怕临时挂过一次、发过链接给别人）？**
>
> - **没有** → 什么都不用做，本次改动已经足够。
> - **有，但当时访问量极小/只是自己测** → 立刻执行 3.5 的换密钥流程，并翻一下 `message`（留言）表和 `orders` 表有没有陌生记录。
> - **有，而且已经跑了一段时间** → 同上，且必须假设后台已被访问过，逐项核对管理员账号、商品、订单是否被改动。

### 3.5 上线时的正确动作（照做即可）

```bash
# 第 1 步：生成一个真正随机的密钥（每次执行结果都不同，别抄任何文档里的示例值）
python -c "import secrets;print(secrets.token_urlsafe(48))"

# 第 2 步：写进服务器上的 server/.env（这个文件永远不会进 git）
MAI_ISLE_ENV=production
MAI_ISLE_SECRET=<把第 1 步的输出粘这里>
MAI_ISLE_DEBUG=0
MAI_ISLE_CORS=https://你的域名.com

# 第 3 步：把后台密码从 admin123 改掉（登录后台 → 修改密码）
# 第 4 步：重启后端。如果密钥没配好，进程会直接起不来并告诉你缺什么
```

**换密钥的副作用（属于期望行为）**：所有已登录用户会被强制登出，需重新登录。因为这等于换了印章，旧章盖的凭证一律失效。

## 四、放在个人 GitHub 作品集上到底有什么用

说实话，作用分两种，取决于你怎么用：

### 4.1 它真正值钱的地方（对你投产品岗）

| 价值 | 说明 |
|------|------|
| **证明"能把模糊需求推到交付"** | 产品岗最怕遇到"只会写 PRD 不会落地"的人。你有 PRD→原型→数据库→接口契约→技术文档→验收报告**完整链路**，这是最稀缺的证据 |
| **面试官能自助核实** | 面试时一句"细节我都放仓库了，链接在这"，比口头描述可信度高一个量级 |
| **AI 协作能力的实证** | 2026 年招聘里这是差异化项。但**要主动说明**，别让人误以为你手写了全部代码——被拆穿的代价远大于收益 |
| **可反复引用** | 一个链接用三年，不用每次重新准备材料 |

### 4.2 它不会帮你做的事（别抱幻想）

- ❌ **不会让 HR 加分**：初筛 HR 平均看一份简历 20–30 秒，基本不会点 GitHub 链接
- ❌ **不会替代在线可访问的演示**：面试官不会为了看你项目去装 Python 环境
- ❌ **产品岗不看代码质量**：你后端分层再规范，产品面试官也判断不了

### 4.3 所以真正该补的两件事（按性价比排序）

| 优先级 | 动作 | 为什么 |
|--------|------|--------|
| **1** | **做一个"能直接点开看"的在线演示**（GitHub Pages 放静态前台 / 或录 60 秒操作视频放 README 首屏） | 这是把"代码仓库"变成"作品"的唯一跳跃。HR 和面试官只吃这一套 |
| **2** | **补齐仓库元信息**：Description 一句话、Topics 标签、README 首屏放 3 张截图 | 让人 3 秒内明白"这是什么、做了什么、效果如何" |

> 补完这两件事，这个仓库才算"作品集"；只把代码传上去，它只是一个"备份"。

## 五、简历里怎么写这个链接

### 5.1 写法（放在项目经历标题行末尾）

```
麦屿手作（Mai-Isle）品牌官网及后台管理系统 ｜ 产品负责人
2026.07–2026.09 ｜ 作品：github.com/XCT-111xct/mai-isle-cake-shop
```

### 5.2 三条注意事项

| 注意 | 说明 |
|------|------|
| **只写"作品"或"仓库"，不要写"独立开发"** | 你主导的是需求、规范、验收；技术实现为 AI 协作完成。写"独立开发"面试官一问技术细节就露馅 |
| **不要放在简历最显眼的技能区** | 产品岗简历的价值顺序是：项目成果 > 方法论 > 作品链接。链接放项目末尾，别抢主位 |
| **面试时主动交代 AI 协作** | 说"我用 AI 完成了编码，自己负责需求定义、规范设计和逐项验收"——这是**加分**（体现工具驾驭力）；被追问才承认，就成了**减分**（诚信问题） |

### 5.3 面试官大概率会问的 3 个问题（提前准备）

1. **"这个后台是给谁用的？为什么不做在线支付？"** → 答：单店烘焙品牌，客单价中等、复购靠电话/微信私域，在线支付要接支付渠道+退款+对账，成本高于收益，本期明确划出边界。
2. **"你怎么验收的？"** → 答：19 项验收清单 + 105 个自动化测试用例，逐条对 PRD；两类前端缺陷固化成防复发清单强制回归。
3. **"代码是 AI 写的，你做了什么？"** → 答：（这题要坦荡）需求定义、字段级校验规则、订单状态机、双层权限模型、6 份规范文档、逐轮评审和最终验收——AI 负责实现，我负责定义和判断对错。
